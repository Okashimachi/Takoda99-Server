### これは何のプロジェクトか

**タコダ99** — 99人同時対戦のたこ焼き屋タイピングゲーム。ハッカソン本戦は **2026-08-24**。
あなたが触るのは **Go のゲームサーバー**（`Takoda99-Server`）、特に**バランス検証シミュレータ**。

- プレイヤーは客に注文され、**お題（ひらがな）を打鍵**して提供する
- スコア `= weightTakoyaki × 提供数 − weightMiss × ミス数`（int・負値もありうる）
- **20秒ごとに下位を足切り**。99→75→55→35→20→10→0 と減り、**120秒で全店脱落＝試合終了**
- `internal/sim` は**99店ぶんの仮想プレイヤーを動かして試合を丸ごと回す**。
  `make sim` で決着時間・分離度・負スコア発生率・実力相関を出す

### 今回の修正目的

**バランス調整の判断はすべて sim の数字を根拠に決めている**（h26 の `weightMiss=25` も）。
その sim の仮想プレイヤーに問題が2つある。

```go
case ProfileNormal:
    msPerKey = 200 + int(rng.NormFloat64()*50)              // 独立の乱数
    missRate = clamp(0.05+rng.NormFloat64()*0.02, 0, 0.5)   // 独立の乱数
```

- **速度とミス率が無相関**なので、「130ms/打鍵なのにミス率9%」「300ms/打鍵なのにミス率1%」
  という**実在しない個体**が生まれ、それが順位表の上下を作っている
- **難度が上がっても `msPerKey` が変わらない**ので、sim は**終盤を楽観的に見積もっている**

**モデルを実プレイに寄せ、sim の結論を信じられるようにする。**

### 🔴 コード上の制約（破ると壊れる）

| 制約 | 理由 |
|---|---|
| 🔴 **決定性を壊さない**（同じシードで同じ結果） | **sim の全結論の前提**。乱数の消費順序を変えると過去の数字と比較できなくなる |
| **既存の良い実装を壊さない** | ミスは**打鍵ごとに判定**、`elapsedMs` は**ミスの打ち直しを含む**、打鍵数は `odai.Keystrokes` で**正確に数える**。どれも理由があってそうなっている（§0.1） |
| **`duel` プロファイルは相関から外す** | あれは「速いが雑 vs 遅いが正確」の**極端な2型をあえて作って比率を測る道具**。現実の母集団を模すものではない。h26 の検証が壊れる |
| **`internal/game` は `sim` を知らない**（AGENTS.md §4.2） | 依存は `sim → game` の一方向。逆流させない |
| **h31 とモデル実装を1箇所に共有する**（§3） | 別々に書けば必ずズレ、**今と同じ状態に戻る**。先に着手した方が共有関数を作り、後発はそれを使う |
| **proto を変えない** | sim は proto のメッセージを組み立てて session に流すが、**契約は既存のまま** |
| **`main` へ直 push しない** | ブランチを切って PR。1 plan = 1 PR |

### 設計意図（なぜこう直すか）

- **「実力」を1つのスカラー（`skill`）にする**のが中核。乱数を振るのは `skill` 1本だけにして、
  そこから速度とミス率を導けば**自動的に相関する**。プロファイルは
  「`skill` をどう分布させるか」の指定に格下げされる
- **難度追従を `skill` に反比例させる**（上手い人ほど難度に強い）。
  これで「終盤に下位が崩れる」という自然な淘汰が sim にも現れる
- **人間の完全再現は狙わない。** 目的は「**h26 の重み判断を信じられるようにする**」こと。
  疲労・ウォームアップ・打鍵間隔の分布は**やらない**（§1.3）
- 🔴 **数字が動くのは失敗ではない。** むしろ「今までの sim が現実とズレていた」ことの証拠であり、
  本 plan の成果。動かなければ h26 の判断が頑健だったということ

### 進め方と完了の定義

`main` へ直 push しない。末尾「§6 完了条件」を全て満たし、`make check` が緑。
**§5（h26 の結論の再測定）まで含めて完了**——モデルを変えたら過去の判断を測り直す。
結論が変わったら `plan-h26` に**追記**する（消さずに「h33 で再測定した結果」として残す）。
PR 後に `gh pr checks <N>` で CI 実走・緑を確認する。

## 0. 現状の測定（コードを読んだ結果）

### 0.1 すでに良くできている点（壊さないこと）

`internal/sim/dummy.go` は、思っていたより実プレイに近い:

| 項目 | 実装 | 評価 |
|---|---|---|
| ミス数 | **打鍵ごとに判定**（`for i := 0; i < keys; i++`） | ✅ 正しい |
| 所要時間 | `(keys + miss) * msPerKey` | ✅ **ミスの打ち直しを含む**。実クライアントと定義が揃っている |
| 打鍵数 | `odai.Keystrokes` で**実際の打鍵数**を数える | ✅ ルーン数概算だと speed が上限に張り付く、と理由まで書かれている |

> ⚠ **実 Bot（`internal/bot`）の方が粗い**。あちらは `miss ∈ {0,1}` の固定で、
> **sim の方が現実に近い**という逆転が起きている。これは h31 §2.2 で解消する。

### 0.2 直すべき点

#### ① 🔴 速度とミス率が**独立**に振られている

```go
case ProfileNormal:
    msPerKey = 200 + int(rng.NormFloat64()*50)              // 独立の乱数
    missRate = clamp(0.05+rng.NormFloat64()*0.02, 0, 0.5)   // 独立の乱数
```

**2本の乱数が無相関**なので、次のような個体が生まれる:

- 「**130ms/打鍵で打てるのにミス率9%**」＝ 超高速なのに雑
- 「**300ms/打鍵と遅いのにミス率1%**」＝ 遅いのに完璧

現実のタイピングでは**速い人ほど正確**（正の相関）。無相関で振ると、
分布の四隅に**実在しない個体**が置かれ、それが順位表の上下を作ってしまう。

> これは h26 の `weightMiss` 判定に直接効く。「速度型 vs 正確型」の比率を測っていたが、
> **母集団の相関構造がそもそも現実と違う**なら、比率の最適値もズレる。

#### ② 難度が上がっても速度が落ちない

`msPerKey` は試合中**一定**。heat が 0→17 に上がっても、1打鍵あたりの速度は変わらない。

- 語が長くなるぶん総時間は伸びる（ここは正しい）
- しかし**「難しい語は1打鍵あたりも遅くなる」**という人間の性質が入っていない
- 同様に、**難しい語ほどミス率が上がる**のも入っていない

**結果**: sim では終盤も序盤と同じ調子で打ち続ける。実プレイの終盤（heat 13〜17）は
もっと崩れるはずで、**sim は終盤を楽観的に見積もっている**。

#### ③ プロファイルが「実際の卓」を模していない

```
uniform / normal / bipolar / wide / duel
```

どれも**人工的な分布**で、「Bot 99体＋人間数名」という**本番の卓**を再現するものが無い。

## 1. 方針

```
現状: 速度とミス率が独立・難度非追従の仮想プレイヤー
本案: 1つの「実力」から速度とミス率を導き、難度で両方を劣化させる
```

### 1.1 「実力」を1つのスカラーにする ★中核

```
skill ∈ [0, 1]     // 0 = 苦手  1 = 上手い

msPerKey = lerp(slowMsPerKey, fastMsPerKey, skill)
missRate = lerp(highMissRate, lowMissRate, skill)
```

**乱数を振るのは `skill` 1本だけ。** これで速度とミス率が自動的に相関する。
プロファイルは「`skill` をどう分布させるか」の指定に格下げされる。

| プロファイル | skill の分布 |
|---|---|
| uniform | 全員 0.5 |
| normal | 正規分布（平均0.5・σ0.15） |
| bipolar | 0.2 と 0.8 の二山 |
| wide | 一様 [0, 1] |

> **duel（速度型 vs 正確型）だけは相関から外す。** あれは
> 「速いが雑」「遅いが正確」という**極端な2型をあえて作って比率を測る道具**であり、
> 現実の母集団を模すものではない。h26 の検証をそのまま残すために**別扱いにする**。

### 1.2 難度追従を入れる

```
実効msPerKey = msPerKey × (1 + difficultyPenalty × heatLevel)
実効missRate = missRate × (1 + difficultyPenalty × heatLevel)
```

**`difficultyPenalty` は skill に反比例させる**（上手い人ほど難度に強い）:

```
difficultyPenalty = lerp(0.04, 0.01, skill)
```

これで「終盤に下位が崩れる」という**自然な淘汰**が sim にも現れる。

### 1.3 やらないこと

| 案 | 判断 |
|---|---|
| 疲労（時間経過で劣化） | **やらない**。難度追従と効果が重複し、切り分けられなくなる |
| ウォームアップ（序盤は遅い） | **やらない**。試合が120秒しかなく、効果が測定誤差に埋もれる |
| 打鍵間隔のゆらぎ（分布を持たせる） | **やらない**。平均が同じなら順位への影響は小さい。計算量だけ増える |

> 目的は「**h26 の重み判断を信じられるようにする**」であって人間の完全再現ではない。
> ①相関 と ②難度追従 の2つが、順位に効く支配的な要因。

## 2. 本番の卓を模したプロファイルを足す

```
--profile match     // Bot 99体の tier 分布 ＋ 人間数名
```

- Bot は h31 の tier 配分（弱25% / 中50% / 強25%）を `skill` に写す
- 人間を数名混ぜ、**その人間が何位に来るか**を出力する

**これが本 plan の実用的な目的。** 「人間が真ん中あたりに来る」を数字で確認できる。

| 出力 | 意味 |
|---|---|
| 人間の平均順位 | 40〜60位あたりが目標（99人中） |
| 人間の脱落ステージ | どの足切りで落ちるか |
| 人間が1位になる確率 | 高すぎ／低すぎないか |

## 3. 🔴 h31 とモデルを共有する（二重実装にしない）

h31（実 Bot）と本 plan（sim）は**同じ人間モデル**を実装することになる。
別々に書くと必ずズレて、**sim の予測が実 Bot と合わなくなる**（今まさに起きている状態）。

**共有する形にする:**

```
どちらからも使える純粋関数として置く（例: internal/game か、依存の無い小さなパッケージ）
    skill → (msPerKey, missRate, difficultyPenalty)
    (msPerKey, missRate, heatLevel, keystrokes, rng) → (elapsedMs, missCount)
```

- **`internal/game` は `bot` も `sim` も import してはいけない**（AGENTS.md §4.2）が、**逆は良い**
- 置き場所は実装時に判断してよい。**要件は「1箇所にある」こと**

> h31 と本 plan を**別セッションで実装する場合、先に着手した方がこの共有関数を作る**。
> 後発は既存を使う。両方が独自実装したら、それはこの plan の失敗。
