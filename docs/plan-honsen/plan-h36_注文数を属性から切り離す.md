# Plan-h36: 注文数を属性から切り離す（たこ焼きの個数を独立した抽選にする）

> **目的**: アート要望で「客が注文するたこ焼きは複数段階（2/4/8 など）」にしたい。
> 現在は**注文数が客の属性と1対1で紐づいている**ため、見た目を増やさずに個数だけを変えられない。
> **注文数を独立した抽選表にし、個数も出現率も config から触れるようにする。**
> **依存**: なし（h30〜h35 はすべてマージ・デプロイ済み）
> **正典**: [01_本選企画書 3.8](../../../Takoda99-Docs/00_本選差分/01_本選企画書.md)（スコア＝たこ焼きの数）
> **範囲**: `internal/game/params.go` ・ `internal/game/session.go` ・ **takoda99-config**（別リポ）

## ▶ このファイル単体を実装プロンプトにする場合

以下をそのまま実装セッションの最初のプロンプトにできる。

### これは何のプロジェクトか

**タコダ99** — 99人同時対戦のたこ焼き屋タイピングゲーム。ハッカソン本戦は **2026-08-24**。
あなたが触るのは **Go のゲームサーバー**（`Takoda99-Server`）と、**設定変更用の管理画面**（`takoda99-config`, Next.js）。

- プレイヤーは客に注文され、**お題（ひらがな）を打鍵**して提供する
- **1語 = たこ焼き1個**。スコア `= weightTakoyaki × 個数 − weightMiss × ミス数`
- **客ひとりぶんを全部打ち切って初めて加点される**（途中まで打っても0点。客は逃げない）
- **20秒ごとに下位を足切り**。99→75→55→35→20→10→0 と減り、**120秒で全店脱落＝試合終了**

### 今回の修正目的

**注文数（＝たこ焼きの個数）が客の属性と1対1で固定されている。**

```go
spec := s.rollAttribute()          // 属性を抽選し
s.customers[cid] = &customer{
    attribute:  spec.Attribute,
    orderCount: spec.OrderCount,   // ★ 個数も同じ spec から来る
}
```

そのため「クレーマーは必ず2個」「JK は必ず6個」となり、**見た目を増やさずに個数の段階だけを増やせない**。
アート側は「たこ焼きの舟のアニメはキャラと独立している」ため、**個数を属性から切り離してよい**と確認済み（2026-08-18）。

**注文数を独立した抽選表にし、個数も出現率も config から触れるようにする。**

### 🔴 コード上の制約（破ると壊れる）

| 制約 | 理由 |
|---|---|
| **`GameParameters` の全フィールドは `==` 比較可能**（map/slice 禁止・**配列は可**） | 設定の変更検知を `==` でやっている。抽選表は**固定長配列**で持つこと |
| 🔴 **`backfillDefaults` の補完は「グループ単位」**（フィールド単位ではない） | **本 plan で最も危険な箇所。** 本番DBには `customer` グループが既にあるので、**そこへ足した新フィールドは補完されずゼロのまま**になる。§3 の対処が必須 |
| 🔴 **ゼロを `Validate` で弾かない** | 弾くと `Load` が失敗し `DefaultParameters()` へ落ちる＝**全設定が内蔵デフォルトへ巻き戻る**（#124 と同じ）。`EffectiveX()` で読み替える（h35 の `EffectiveWarnMaxIds` / h31 の `EffectiveTiers` と同じ形） |
| **配列はゼロ埋めされうる** | config から2要素で保存されると3つ目が `{0,0}` になる。`EffectiveX()` が要素単位で吸収すること |
| **既定値は必ず2リポで揃える** | サーバーと管理画面の既定値がズレると、**DBに無いキーが管理画面側の値で保存される**（`perElapsedSec` で実際に事故った）。`npm test` に既定値の一致検査がある |
| **`internal/game` は他の部品を import しない**（`odai`/`bot`/`db` を知らない） | 純粋コア |
| **proto を変えない** | `CustomerArrived` は**既に客ごとに `orderCount` を送っている**ので、切り離してもワイヤは1ビットも変わらない（§1.2） |
| **`main` へ直 push しない** | ブランチを切って PR |

### 設計意図（なぜこう直すか）

- **見た目と量を独立させる。** 属性は h21 で「**ゲームに一切影響しない見た目専用**」と決めた。
  にもかかわらず個数だけが属性に残っていて、**演出の都合が難度に波及する**構造になっていた。ここを解く
- **個数も出現率も config に出す。** 当日「もう少し軽く」「段階をはっきり」が起きたときに、
  ビルドせず次の試合から変えられるようにする（本戦当日にビルドすると進行中の試合が消える）
- **段階数は3で固定する。** 可変長にすると `==` 比較可能を保てず、config のゼロ埋め事故も増える。
  3段階あれば「軽い・普通・重い」は表現できる

### 進め方と完了の定義

`main` へ直 push しない。末尾「§8 完了条件」を全て満たし、`make check` と `make sim` が緑。
PR 後に `gh pr checks <N>` で CI 実走・緑を確認する。

## 0. 現状の測定（実測）

### 0.1 いまの注文数の分布

本番の実値（`/api/params`）:

| 属性 | 個数 | 出現率 |
|---|---|---|
| Normal（通常客） | 3個 | 70% |
| Bonus（ヒョウ柄おばちゃん） | 3個 | 15% |
| Claimer（クレーマー） | 2個 | 10% |
| Buzz（バズ客・JK） | 6個 | 5% |

```
個数でまとめると   2個 : 10%    3個 : 85%    6個 : 5%
加重平均 3.05個
```

**すでに3種類あるが、85%が3個に偏っていて体感はほぼ「3個固定」。**

### 0.2 なぜ属性から切り離す必要があるか

`initCustomers` が**属性の抽選結果から個数も取っている**（`internal/game/session.go`）:

```go
spec := s.rollAttribute()
s.customers[cid] = &customer{attribute: spec.Attribute, orderCount: spec.OrderCount}
```

したがって:

- **個数の段階を増やす＝属性を増やす**ことになり、キャラの追加が必要になる
- 逆に「同じキャラでも個数が違う」が表現できない
- 属性は h21 で「ゲームに一切影響しない見た目専用」と決めたのに、**個数だけが例外的に難度へ効いている**

### 0.3 「8個固定」を測った結果（この plan の発端）

アート要望は当初「8個固定」だった。実測すると**成立しない**:

| | 提供客数 | 実力相関 | 上位/下位 |
|---|---|---|---|
| 現在（2/3/6・平均3.05） | 1306 | **0.96** | 4.2倍 |
| **8個固定** | **614** | **0.88** | **6.4倍** |
| 2/4/8 をほぼ均等（平均4.7） | 1201 | **0.93** | 4.5倍 |

**8個固定の問題は2つ。**

1. **決勝が成立しない。** 終盤（heat 17）は1語約43打鍵なので 8個 = 348打鍵 ≒ **70秒**。
   決勝（100〜120秒）は20秒しかなく、**決勝で配られた客は誰も打ち切れない**
2. **運ゲー化する。** 捌ける客が半減し、実力相関が 0.96 → 0.88 に落ちる。
   **打ち切らないと0点**なので、遅い人は「ずっと打っているのに0点」になる

**2/4/8 を混ぜると解消する。** 2個の客が「必ず達成できる客」として残るため。

## 1. 方針

```
現状: 属性を抽選 → その属性に固定された個数を使う
本案: 属性を抽選（見た目）＋ 個数を別に抽選（難度）
```

### 1.1 個数は独立した抽選表で持つ

```go
// OrderTierCount は注文数の段階数。3段階で固定する（§設計意図）。
const OrderTierCount = 3

// OrderTier は「たこ焼き何個の客が、どれくらいの割合で出るか」。
type OrderTier struct {
    Count  int `json:"count"`  // たこ焼きの個数（= 打つ語数）
    Weight int `json:"weight"` // 出現の重み
}

// CustomerParams に足す
OrderTiers [OrderTierCount]OrderTier `json:"orderTiers"`
```

**既定値**（§0.3 の実測にもとづく）:

| 段階 | 個数 | 重み | 意図 |
|---|---|---|---|
| 軽い | **2** | **35** | **必ず達成できる客**。遅い人が0点で終わらない担保 |
| 標準 | **4** | **35** | 母数 |
| 重い | **8** | **30** | アート要望の「8個」。達成すると大きい |

> **平均 4.50個**（2026-08-18 に企画側が決めた配分）。10試合の実測:
> 決着 120.0s / 提供 1206 / 分離度 4453 / **実力相関 0.95** / 負スコア 0 / 早期切り事故 0。

**配分そのものはバランスにほとんど影響しない。** 8個の割合を 10%〜40% まで振って測ったが、
実力相関は 0.94〜0.95 で動かなかった:

| 配分（2/4/8） | 平均個数 | 提供 | 実力相関 |
|---|---|---|---|
| 40 / 50 / 10 | 3.60 | 1187 | 0.95 |
| 25 / 50 / 25 | 4.50 | 1155 | 0.94 |
| **35 / 35 / 30** | **4.50** | **1206** | **0.95** |
| 20 / 40 / 40 | 5.20 | 1107 | 0.94 |
| 33 / 34 / 33 | 4.66 | 1220 | 0.95 |

効いているのは**8個の割合ではなく「軽い客が存在すること」**。8個が何割来ても、
間に2個の客が挟まれば「達成できないまま終わる」状態にならない。

> 🔴 **したがって守るべき制約は1つだけ。「最も軽い段階（2個）を消さないこと」。**
> 4/6/8 のように全段階を重くすると、8個固定と同じ問題（実力相関 0.88）が戻る。
> **管理画面のヘルプにこの制約を明記すること。**

### 1.2 proto もクライアントも変わらない

`CustomerArrived`（= `CustomerView`）は**既に客ごとに `orderCount` と `words[]` を送っている**。
契約書にも次のように書いてある:

> ★`orderCount` は属性ごとに違い、当日も config で変わる。**固定値を前提にしないこと。**

したがって**切り離してもワイヤは1ビットも変わらない**。proto の3言語ミラー改訂も、クライアント修正も不要。

> ⚠ ただし `docs/client-integration.md` の説明文（「属性ごとに違い」）は**事実と食い違う**ようになるので、
> 「**属性とは無関係に抽選される**」へ直すこと（§6.2）。

### 1.3 `AttributeSpec.OrderCount` は削除する

残すと「効かないツマミ」になる（AGENTS.md が最も嫌う状態）。**削除する。**

- `Validate` の `spec.OrderCount <= 0` チェックも削除
- config-front の入力欄も削除
- 本番DBに残った旧キーは**未知キーとして無視される**（h31 で `bot.baseElapsedMs` を削除したときと同じ）

## 3. 🔴 backfill されない（本 plan で最も危険な箇所）

`backfillDefaults` の補完は**グループ単位**で、グループ全体がゼロのときだけ既定値を入れる。
**本番DBには `customer` グループが既にある**ので、そこへ足した `orderTiers` は**ゼロのまま読まれる**。

```
本番DBの customer = {total, normal, bonus, claimer, buzz}   ← グループは非ゼロ
  → backfillDefaults はこのグループに触らない
  → orderTiers = [{0,0}, {0,0}, {0,0}]
  → 対処が無いと「注文数0個の客」が5000人生まれる＝試合が壊れる
```

**h35（`cull.warnMaxIds`）・h31（`bot.tiers`）と同じ二重防御にする。**

1. **`CustomerParams.EffectiveOrderTiers()`** — ゼロを**要素単位**で既定へ読み替える。
   DBを経由しない sim・テスト・DB無し起動でも安全。呼び出し側は必ずこれを通す
2. **`db.backfillNewFields()`** — `Validate` の**前**に走り、上記を当てる

> 🔴 **`Validate` でゼロを弾かないこと。** 弾くと本番DBが `Validate` に落ちて
> `score` / `cull` / `heat` を含む**全設定が内蔵デフォルトへ巻き戻る**（#124 と同じ経路）。
> 弾くのは**負値**だけにする。

**検証**（h31 の `TestBackfillNewFields_BotTiersFromLegacySchema` を複製する形で）:

- 本番相当の JSON（`customer` は旧スキーマで `orderTiers` が無い）から復元し
  ①ゼロで読まれる ②グループ単位では埋まらない ③**`Validate` が落ちない**
  ④補完後に既定が入る ⑤`score`/`cull`/`heat` が変化しない、を全部固定する

## 5. やらないこと

- **段階数を可変にする**（`[]OrderTier`）。`==` 比較可能を保てず、ゼロ埋め事故も増える
- **属性ごとに個数の傾向を持たせる**（「JK は重い側が出やすい」など）。
  組み合わせが増えるだけで、アート側は独立で問題ないと確認済み
- **proto の変更**。§1.2 のとおり不要
- **語ごとの加点**（打ち切らなくても部分点）。proto 変更＋クライアント修正が要り、本戦に間に合わない
