### これは何のプロジェクトか

**タコダ99** — 99人同時対戦のたこ焼き屋タイピングゲーム。ハッカソン本戦は **2026-08-24**。
あなたが触るのは **Go のゲームサーバー**（`Takoda99-Server`）と、**運営用の観測ダッシュボード**（`Takoda99-DashBoard`）。

- プレイヤーは客に注文され、**お題（ひらがな）を打鍵**して提供する
- スコア `= weightTakoyaki × 提供数 − weightMiss × ミス数`（int・負値もありうる）
- **20秒ごとに下位を足切り**。99→75→55→35→20→10→0 と減り、**120秒で全店脱落＝試合終了**
- **人間は数名で、残りは Bot**。ダッシュボードは運営が試合中に99店の状態を俯瞰するための画面で、
  サーバーが `AdminSnapshot` を `/admin/ws` で配信する

### 今回の修正目的

**h30〜h33 で調整をするのに、その効果を確認する手段が無い。**

### 🔴 コード上の制約（破ると壊れる）

| 制約 | 理由 |
|---|---|
| **`internal/game` は Bot も tier も知らない**（AGENTS.md §4.2） | tier は**合成ルート（`app.RunMatch`）→ `room` → snapshot** の経路で渡す。`IsBot` と同じ流儀 |
| **`room.SetBotIds` には既存の呼び出し元がある** | シグネチャを変えるなら**全部直す**。安全側に倒すなら `SetBotTiers` を**足す**（既存は残す） |
| **`IsBot` フィールドを消さない** | `tier != ""` で導出できるが、ダッシュボードと `store.Result` の**両方が使っている**。消すと余計な変更が波及する |
| **`AdminSnapshot` は proto ではない** | `/admin` 系は Server ↔ DashBoard の**独自コントラクト**。proto の3言語ミラーとは別で、**人間の承認は不要**。ただし**2リポの契約**ではあるので同時に直す |
| **配信の状態は publisher が持つ**（h23 の原則） | **heat の履歴をサーバーに持たせない**。スナップショットは1〜2秒間隔で届くので、**ダッシュボード側で積む** |
| 🔴 **DashBoard の PR は `main` 宛てにする** | 過去に別ブランチ宛てで出して**孤児化した事故**がある（h02 が `main` に載らなかった） |
| **`main` へ直 push しない** | ブランチを切って PR |

### 設計意図（なぜこう直すか）

- **見えないものは調整できない。** 本 plan は単体では機能を増やさないが、
  **h30〜h33 の成果を測る唯一の手段**。これが無いと調整が勘になる

- **人間の行をハイライトする。** 「人間が真ん中に来るか」が h30〜h33 の最重要指標なのに、
  今は99行から目で探すしかない

末尾「§6 完了条件」を全て満たし、`make check` が緑。

## 0. 現状（コードを読んだ結果）

`AdminStore` が持つのは:

```go
Score / TakoyakiCount / MissCount    // ✅ 内訳まで見える（h25 で入れた）

QueueLen / ServedCount / AtRisk / QueueByAttr
```

Bot の識別は `app.RunMatch` の `botIds` → `room.SetBotIds` → snapshot、という経路で通っている
（`game` は Bot を知らない・AGENTS.md §4.2）。**この経路に tier を載せれば済む。**

## 1. サーバー側の変更

### 1.1 `AdminStore` に tier を足す

```go
// Tier は Bot の強さ段階（plan-h31）。人間は空文字。
// IsBot と同じく、game は tier を知らない（AGENTS.md §4.2）ので
// 合成ルート（app.RunMatch）から room 経由で渡す。
Tier string `json:"tier,omitempty"`   // "weak" | "normal" | "strong" | ""（人間）
```

**配線**: `SetBotIds(map[PlayerId]bool)` を **`SetBotTiers(map[PlayerId]string)`** に置き換える
（`IsBot` は `tier != ""` で導出できるが、**`IsBot` フィールドは残す**——
ダッシュボードと `store.Result` の両方が使っており、消すと余計な変更が波及する）。

> ⚠ `room.SetBotIds` は `scale_test.go` など既存テストから呼ばれている可能性がある。
> **シグネチャを変えるなら呼び出し元を全部直す**。安全側に倒すなら `SetBotTiers` を**足す**（`SetBotIds` は残す）。

### 1.2 `AdminSnapshot` に heat 履歴と平均打鍵数を足す

```go
// HeatLevel は現在の難度。既存（あれば）。
// AvgKeystrokes は直近に配った客1人あたりの平均打鍵数（plan-h30 の効果確認用）。
AvgKeystrokes int `json:"avgKeystrokes"`
```

**heat の履歴はサーバーに持たせない。** スナップショットは1〜2秒間隔で届くので、
**ダッシュボード側で受信のたびに配列へ積めばよい**（サーバーに状態を増やさない）。

> h23 で「配信の状態は publisher が持つ」と決めた原則に沿う。
> 履歴はビューの都合なので、ビュー側の責務。

## 2. ダッシュボード側の変更

### 2.1 tier の色分け（4値）

```
現状: Bot / 人間 の2色
本案: 弱Bot / 中Bot / 強Bot / 人間 の4色
```

- **スコア分布ビュー**（h25 で作った）の各点を tier で塗る
- 一覧表に tier 列を足す

**これで一目で分かること:**

| 見たい | 見え方 |
|---|---|
| 強 Bot が上位を独占していないか | 上位帯が1色に染まっていたら失敗 |
| 人間がどの層に混ざっているか | 人間の色が中央付近にあれば目標達成 |
| 弱 Bot が早期に落ちているか | 足切りのたびに弱の色が減る |

### 2.2 heat カーブのグラフ

受信したスナップショットの `heatLevel` を時系列で描く。

- **上限（`maxLevel`）を水平線で引く** → 届いたかが一目で分かる（h32 の①②③がここで確認できる）
- 足切り時刻に縦線 → 段差がどこで起きたか分かる

> h32 で「上端に届かない」問題が**3回目**の再発だった。**目で見えれば4回目は起きない。**

### 2.3 平均打鍵数の表示

`avgKeystrokes` を数値で出す。h30 で「1語45打鍵以下」にした効果が、
**実試合で本当に効いているか**を確認する唯一の手段。

## 3. 視認性の改善（エンジニアUX）

h25 のダッシュボードは情報量を優先しており、**調整作業には向いていない**。

| 改善 | 理由 |
|---|---|
| **tier 別の集計を上部に出す**（各tierの平均スコア・生存数） | 99行の表から目で拾うのは無理。**平均値1行**で傾向が分かる |
| **人間の行をハイライト**する | 「人間が何位か」が本 plan 群の最重要指標。探させない |
| **足切りラインを表に引く** | 次の `targetAliveCount` の位置に線。誰が危ないかが即分かる |

> ⚠ **見た目の作り込みは最小限にする。** 当日運用で使うのは「順位・tier・heat」の3つ。
> 凝ったUIは本戦当日(2026-08-24)までの時間を食う。
