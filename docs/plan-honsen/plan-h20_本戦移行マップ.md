# Plan-h20: 本戦ルール移行マップ（実装セッションはまずこれを読む）

> **目的**: 本戦ルール（スコア制・時刻足切り・120秒全店脱落）への移行を、**Server / config / DashBoard の3リポ横断**で破綻なく進めるための地図。h21〜h26 が跨いで共有する決定をここに1本化する。
> **性格**: 新機能の plan ではなく、**移行そのものの設計**。順序を守らないと CI が赤いまま進むことになる。
> **正典**: `Takoda99-Docs/00_本選差分/`（企画の正典）／ `plan-h10`（proto v0.8.0・承認済み）
> **前提**: proto **v0.8.0 タグ済み**。Server main に h01・h02 マージ済み（#106 / #107）。

## ▶ この plan 群をプロンプトとして使う（実装セッション向け）

各 plan は**単体でプロンプトにできる**ように書いてある（前提チェック・進め方・完了条件を内蔵）。
新しい実装セッションでの標準手順:

1. **先に読む**: リポジトリ直下 `AGENTS.md`（憲法）→ `docs/architecture.md` → 本書（h20）。
2. **着手する plan の「▶ 実装プロンプトにする場合」ブロックの前提チェック**を実行し、満たさなければ依存 plan を先に。
3. **1 plan = 1 ブランチ = 1 PR**。`main` へ直 push しない。
4. **完了の定義は各 plan 末尾の「完了条件」**。記載のコマンド（`go test` / `golangci-lint run` 等）が緑になって初めて完了。
5. **PR を出したら CI が実際に走って緑になったことを確認**（`gh pr checks <N>`）。checks が 0 件のままマージしない。
   スタックして発火しない場合は **PR を close → reopen** で再発火する（今回 #107 で実際に必要になった）。
6. **proto / 契約 / AGENTS.md（憲法）に触るなら、実装前に変更案を人間に提示して承認**（AGENTS.md §7）。
   このトラックは proto は承認・タグ済みだが、**h22 の AGENTS.md 更新は承認が要る**。

> 実装は AI に任せる前提で書いてあるが、**上記1〜6を飛ばすと事故る**。特に 2（前提チェック）と 5（CI 実走確認）。

## 0. なぜ変えるのか — 3リポの変更動機

移行作業の途中で「何のためにこれをやっているか」を見失わないために、最初に書く。

### Server — ルールそのものが変わった

順位を決める値が **評価（EMA×パーセンタイルの相対値）→ スコア（累積の絶対値）** に、脱落が
**storm の tick 周期 → 20秒等間隔の時刻スケジュール** に変わった。予選の「正確に打ったのに負けた」
という納得感の欠如を、**実力以外の要素を勝敗から取り除く**ことで構造的に解消するのが狙い。

> **処理は増えない。むしろ減る。** 監視対象（信用・我慢ゲージ）が2つ消え、EMA と
> パーセンタイル正規化が不要になり、割り込みイベントが2種類減る。**移行は「足す」より「やめる」が主**。

### config（takoda99-config）— 調整すべき数値が変わった

触るべき係数が **`score.weightTakoyaki` / `score.weightMiss` の比率** と
**`cullSchedule` の `targetAliveCount`** に集約された。この2種が本作の面白さの中心で、
残り期間で最も回数を重ねて詰めることになる。

> 🔴 **廃止キーを UI に残したままにしない。** 当日「効かない値」をいじって時間を溶かす事故が起きる。
> 予選で `initialLife` を DB で変えたのにコードの既定値を見ていた、という混乱の再来を避ける。

### DashBoard — 観測の目的が変わった

**「当日のトラブル切り分け」から「残り期間でバランスを詰めるための計測器」へ主目的が移る。**

体力・我慢ゲージの監視は意味を失い、代わりに見るのは
[11_差分_サーバー §7](../../../Takoda99-Docs/00_本選差分/11_差分_サーバー.md) のシミュレーション観測項目：

- 各ステージ時点で**スコア分布が上位と下位に分離しているか**
- **実力上位が早期ステージで切られていないか**（事故率）
- 同実力店の**順位ブレ幅**（お題ランダム性の影響）
- `weightMiss` を変えたとき「速いがミスも多い店」と「遅いが正確な店」のどちらが勝つか

> ダッシュボードは h26（バランス検証）の道具になる。**見えないものは調整できない。**

## 2. 🔴 h20-A: go.mod v0.8.0 化は「3点セット」で1PR

**この3つを同時にやらないと CI が緑にならない。** 検証済みの事実として記録する。

| # | 作業 | やらないと |
|---|---|---|
| 1 | `go.mod` を proto v0.8.0 へ | 新メッセージが使えない |
| 2 | `internal/proto/wire_golden_test.go` の期待値更新 | **7件失敗**（v0.8.0 でフィールド増＋順序変更） |
| 3 | `.golangci.yml` で **SA1019 を一時抑止** | **33件失敗**（`Deprecated:` マーカー由来） |
| 4 | `internal/proto/messages.go` に新型を再輸出 | h23 で `RankingSnapshot` 等が参照できない |

### 2.1 SA1019（deprecated 使用）の内訳

proto v0.8.0 で廃止フィールドに `// Deprecated:` を付けたため、**それを使っている既存コードが全部警告になる**。

| 箇所 | 件数 | 性質 |
|---|---|---|
| `internal/game/session_test.go` | 27 | テスト（移行で書き換わる） |
| `internal/proto/messages.go` | 5 | 再輸出ラッパ（型エイリアスなので実害なし） |
| `internal/app/headless_test.go` | 1 | テスト |

**本体コードはほぼゼロで、大半がテスト**。移行が終われば自然に消える性質のもの。

### 2.2 抑止の書き方と **解除条件**

`.golangci.yml` に SA1019 の除外を足す。**必ず解除条件をコメントに書く**（消し忘れ防止）。

```yaml
# 本戦ルール移行（plan-h20〜h23）の期間だけ SA1019 を抑止する。
#
# proto v0.8.0 で信用・我慢ゲージ・相対評価のフィールドに Deprecated: を付けたが、
# サーバー側の移行はこれから（h21〜h23）。移行前のコードが全部警告になり CI が赤くなるため、
# 移行期間だけ黙らせる。
#
# ★解除条件: h23 完了時（廃止フィールドの参照がサーバーから消えた時点）にこの除外を外す。
#   外した状態で golangci-lint run が緑なら、移行が本当に完了している証拠になる。
```

> **この除外は「移行完了の検知器」を兼ねる。** 外して緑なら完了、赤なら残っている。
> h23 の完了条件に「この除外を外して緑」を入れてある。

> 🔴 **ただし内訳のうち `internal/proto/messages.go` の5件は自然には消えない。**
> ラッパが廃止型（`canon.CustomerLeft` / `canon.CreditUpdate` / `canon.StoreListUpdate` /
> `canon.LeaveReason` / `canon.CreditReason`）を**名指しして再輸出している限り必ず SA1019 になる**ため。
> テスト側の28件は h21/h22 の書き換えで自然に消えるが、この5件は
> **h23 で再輸出そのものを削除する**必要がある（**plan-h23 §5.1**）。
> これをやらないと「除外を外して緑」が永久に達成できない。

### 2.3 再輸出する新型（`internal/proto/messages.go`）

```go
RankingEntry / RankingSnapshot / RankingChange / RankingDelta
StoreEliminatedBatch / CullStageView
TypeRankingSnapshot / TypeRankingDelta / TypeStoreEliminatedBatch
```

`internal/proto` は canonical の**薄い再輸出ラッパ**。独自の型を生やさない（AGENTS.md §1.2）。

## 3. 廃止処理の扱い — **サーバーのコアは「削除」する**

proto は方式B（残して使わない）を採ったが、**サーバー内部のコードは削除**する。

| | proto | サーバーのコア |
|---|---|---|
| 方式 | **B: 残して使わない** | **A: 削除する** |
| 理由 | サーバーとクライアントが別々の時期に移行できる。minor で済む | 下記 |

**サーバーを削除にする理由**

1. **二重経路はテストが倍になる。** `stepPatience` を残してフラグ分岐すると、tick ループの各段に
   「旧」「新」が並び、`internal/sim` の決着保証も両方で回す必要が出る。残り期間でその複雑さは割に合わない。
2. **契約は proto 側の方式Bで守られている。** サーバーが送らなくなっても旧クライアントは壊れない。
   退避弁は既に契約層にある。
3. **当日の退避弁は「前のバイナリに戻す」で足りる。** デプロイは手元クロスコンパイル → アップロード →
   `install` + `systemctl restart` なので、**旧バイナリを1つ保管しておけば数十秒で戻せる**（`docs/deploy.md`）。
   コードにフラグを埋めるより確実。
4. コードは git 履歴に残る。消えてなくなるわけではない。

> ⚠ **ただし「当日の退避弁」は運用として必ず用意する。** h26 の完了条件に
> 「本戦バイナリの1つ前を保管し、戻し手順を runbook に書く」を入れる。

## 4. リポ横断の同期点

### 4.1 DashBoard ↔ Server の webdist

ダッシュボードの実体は **Takoda99-DashBoard リポが正典**で、Server は `internal/admin/webdist/` に
**同梱コピー**を持つ（`//go:embed` で単一バイナリにするため）。

```
Takoda99-DashBoard（正典・ここで編集）
        │ 同期（コピー）
        ▼
Takoda99-Server/internal/admin/webdist/（同梱物・手で合わせる）
```

> 🔴 **これは手動同期であり、必ずズレる。** 実際に h02 の作業中、DashBoard が先にマージされ
> Server 側だけ未マージという非対称が起きた。**h25 では「DashBoard を直す → Server へ再sync」を
> 1つの作業単位として扱い、両方を同じタイミングでマージする。**

### 4.2 Server ↔ config（takoda99-config）

`GameParameters` の**スキーマはサーバーが正典**、config-front はその編集UI。
片方だけ変えると「保存できない」「知らないキーが消える」が起きる。**h24 で同時に扱う**。

DB（Postgres `game_config`）は `backfillDefaults` で不足キーを内蔵デフォルトから補完する仕組みが既にある
（`internal/db/config.go`）。**新キーはこれで自動的に埋まる**が、**廃止キーは DB に残り続ける**点に注意。
