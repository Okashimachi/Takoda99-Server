## 1. 決めるもの

| # | 値 | 仮 | 効き方 |
|---|---|---|---|
| 1 | **`score.weightTakoyaki` : `score.weightMiss`** | 100 : 30 | **速さ重視か正確さ重視か**。本作の性格そのもの |
| 2 | 中間ステージ #2〜#4 の `targetAliveCount` | 55 / 35 / 20 | 脱落カーブの体感 |
| 3 | 初回（#1）の 24% という数字 | 75 | 「20秒で理不尽に落ちない」の担保 |
| 4 | **`heat.phaseLate`（or `heat.maxLevel`）** | 8 / 17 | ★h22 で判明。**辞書上端が本番で使われない**（下記 1.2） |

### 1.2 ★h22 で判明：お題辞書の上端（level 17）が本番で一度も使われない

```
heat = base(0) + int(perAliveDrop(0.1) × (99 − alive)) + Late(8)

生存10店で終了 → int(0.1×89) + 8 = 16   ← 本戦はここで終わる
生存 1店まで削る → int(0.1×98) + 8 = 17  ← 予選はここまで行っていた
```

`matchsim` の実測でも **最終 heatLevel = 16**（最大16）。予選は生存1店まで削ったので 17 に届いていたが、
本戦は**生存10店で終わる**ため、用意した最上位レベルの語彙が死んでいる。

あわせて **`heat.maxLevel = 17` が絶対に binding しないツマミ**になっており、
AGENTS.md の「効かないツマミを残さない」に抵触する。

| 候補 | 効果 | 評価 |
|---|---|---|
| **`heat.phaseLate: 8 → 9`** | 決勝でちょうど 17 に届く（alive=10 で 8+9=17） | **推奨**。Late だけが上がり Early/Mid のカーブは無傷。触る値が1つ |
| `heat.perAliveDrop` を上げる | 中盤以降が全体に上がる | カーブ全体が動くので調整が難しい |
| `heat.maxLevel: 17 → 16` | ツマミが正直になる | 上端の語彙は使わないと割り切る場合 |

> sim で「Late が難しすぎる」と出たら後者（`maxLevel: 16`）へ倒す。**どちらにせよツマミは正直にする。**

**動かしてはいけないもの**（企画で確定）: 20秒等間隔 / 120秒 / #5 の10人 / #1 が20秒より早くならないこと。

### 1.1 重み比率が決めるゲームの性格

| 比率 | ゲームの性格 |
|---|---|
| `weightMiss` が小さい | ミスを恐れず**速く打つ**ゲーム |
| `weightMiss` が大きい | **慎重に正確に**打つゲーム |
| **釣り合っている** | **どちらを取るかの判断が発生する＝狙っている状態** |

## 2. シミュレーションで観測するもの

`cmd/matchsim` を使う（ダミー店99体・打鍵速度とミス率に分布を持たせる）。

```bash
go run ./cmd/matchsim --runs 20 --profile normal
```

| 観測 | 判定の目安 | 対応する保留事項 |
|---|---|---|
| 各ステージ時点の**スコア分布** | 上位と下位が**分離**しているか（団子だと足切りが運になる） | P3 |
| **実力上位が早期に切られる事故率** | 20秒・40秒で上位実力の店が切られていないか | **P1 / P4** |
| **同実力店の最終順位のブレ幅** | お題ランダム性の影響がどれくらいか | P2 |
| **「速いがミスも多い店」vs「遅いが正確な店」の勝率** | **どちらかに偏っていないこと**が目標 | ★最重要 |
| **負のスコアの発生率** | ほぼ 0 であること（h21 §1.1 の副作用の確認） | — |
| ステージごとの淘汰人数 | `targetAliveCount` どおりか | P4 |

> **累積方式にしたことでシミュレーションが単純になった。** EMA の初期不安定・平滑化係数・
> パーセンタイル正規化といった結果を歪める要素が消え、**「速さ型と正確型のどちらが勝つか」という
> 本質的な検証に集中できる**。

### 2.1 ★最重要の検証：速さ型 vs 正確型

ダミー店に2種類のプロファイルを与えて勝率を比べる。

```
速さ型 : 打鍵は速いがミス率が高い
正確型 : 打鍵は遅いがミスがほぼ無い
```

**どちらかが常勝なら比率が偏っている。** 勝率が拮抗し、かつ「その場の判断で切り替える余地がある」
状態が狙い。ここを `weightMiss` で調整する。

## 3. 実プレイでの確認

シミュレーションは**実力分布の仮定**に依存する。人間が入ったときの体感は別途確認する。

| 確認 | 方法 |
|---|---|
| 20秒で切られる人の体感 | 「理不尽」か「納得」か。**予選の"10秒で終わる"体験を潰せているか** |
| 決勝20秒の盛り上がり | 逆転が起きるか。スコア差が開きすぎていないか |
| スコアの伸びの気持ちよさ | 打った実感と数字が一致するか |

> **h25 のダッシュボードで観測しながら回す。** スコア分布ビューとカットラインの重ね表示が、
> この作業の主な道具になる。

## 4. Bot の強さ（P1）

Bot 補完で**常に99人**にするため、**Bot の質が体験を支配する**（人間が少ないほど顕著）。

- Bot が弱すぎる → 人間が上位を独占し、足切りが機能しない
- Bot が強すぎる → 人間が20秒で全滅する

現行 Bot は固定パラメータ（`bot.Config`: `BaseAccuracy` / `BaseElapsedMs` / jitter）で、
**config から調整できる**。当日はこれを手で調整すれば足りる。

> **より本格的な Bot 強化（実データから tier 生成）は h03〜h05（`order_attempt` → プロファイル → tier制）。**
> 本 plan は「当日成立させるための手調整」までを範囲とする。時間が足りなければ h03〜h05 は諦めてよい。
