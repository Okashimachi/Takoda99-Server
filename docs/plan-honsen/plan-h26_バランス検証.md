## 1. 決めるもの

| # | 値 | 仮 | 効き方 |
|---|---|---|---|
| 1 | **`score.weightTakoyaki` : `score.weightMiss`** | 100 : 30 | **速さ重視か正確さ重視か**。本作の性格そのもの |

### 1.2 ★h22 で判明：お題辞書の上端（level 17）が本番で一度も使われない

```
heat = base(0) + int(perAliveDrop(0.1) × (99 − alive)) + Late(8)

生存10店で終了 → int(0.1×89) + 8 = 16   ← 本戦はここで終わる
生存 1店まで削る → int(0.1×98) + 8 = 17  ← 予選はここまで行っていた
```

`matchsim` の実測でも **最終 heatLevel = 16**（最大16）。予選は生存1店まで削ったので 17 に届いていたが、
本戦は**生存10店で終わる**ため、用意した最上位レベルの語彙が死んでいる。

あわせて **`heat.maxLevel = 17` が絶対に binding しないツマミ**になっており、
AGENTS.md の「効かないツマミを残さない」に抵触する。

| 候補 | 効果 | 評価 |
|---|---|---|
| **`heat.phaseLate: 8 → 9`** | 決勝でちょうど 17 に届く（alive=10 で 8+9=17） | **推奨**。Late だけが上がり Early/Mid のカーブは無傷。触る値が1つ |
| `heat.perAliveDrop` を上げる | 中盤以降が全体に上がる | カーブ全体が動くので調整が難しい |
| `heat.maxLevel: 17 → 16` | ツマミが正直になる | 上端の語彙は使わないと割り切る場合 |

> sim で「Late が難しすぎる」と出たら後者（`maxLevel: 16`）へ倒す。**どちらにせよツマミは正直にする。**

**動かしてはいけないもの**（企画で確定）: 20秒等間隔 / 120秒 / #5 の10人 / #1 が20秒より早くならないこと。

### 1.1 重み比率が決めるゲームの性格

| 比率 | ゲームの性格 |
|---|---|
| `weightMiss` が小さい | ミスを恐れず**速く打つ**ゲーム |
| `weightMiss` が大きい | **慎重に正確に**打つゲーム |
| **釣り合っている** | **どちらを取るかの判断が発生する＝狙っている状態** |

## 2. シミュレーションで観測するもの

`cmd/matchsim` を使う（ダミー店99体・打鍵速度とミス率に分布を持たせる）。

```bash
go run ./cmd/matchsim --runs 20 --profile normal
```

| 観測 | 判定の目安 | 対応する保留事項 |
|---|---|---|
| 各ステージ時点の**スコア分布** | 上位と下位が**分離**しているか（団子だと足切りが運になる） | P3 |
| **実力上位が早期に切られる事故率** | 20秒・40秒で上位実力の店が切られていないか | **P1 / P4** |
| **同実力店の最終順位のブレ幅** | お題ランダム性の影響がどれくらいか | P2 |
| **「速いがミスも多い店」vs「遅いが正確な店」の勝率** | **どちらかに偏っていないこと**が目標 | ★最重要 |
| **負のスコアの発生率** | ほぼ 0 であること（h21 §1.1 の副作用の確認） | — |
| ステージごとの淘汰人数 | `targetAliveCount` どおりか | P4 |

> **累積方式にしたことでシミュレーションが単純になった。** EMA の初期不安定・平滑化係数・
> パーセンタイル正規化といった結果を歪める要素が消え、**「速さ型と正確型のどちらが勝つか」という
> 本質的な検証に集中できる**。

### 2.1 ★最重要の検証：速さ型 vs 正確型

ダミー店に2種類のプロファイルを与えて勝率を比べる。

```
速さ型 : 打鍵は速いがミス率が高い
正確型 : 打鍵は遅いがミスがほぼ無い
```

**どちらかが常勝なら比率が偏っている。** 勝率が拮抗し、かつ「その場の判断で切り替える余地がある」
状態が狙い。ここを `weightMiss` で調整する。

### 2.2 【追記 2026-08-16】h30 で `weightMiss` を 25 → 30 に改めた

**本 plan で決めた 25 は、h30（お題カーブの是正）で成立しなくなった。**

h30 で「1語を短く保ち `orderCount` で難度を上げる」形に変えたところ、
同じ基準（速さ型と正確型の**平均順位が拮抗する点**）で測った最適値が動いた:

```
        h26 時点        h30 後
拮抗点   25             30 前後
```

| W_MISS | h30後 平均順位の差 | h30後 上位10の速% |
|---|---|---|
| 18 | −36.1 | 78% |
| 22 | −24.0 | 40% |
| **25** | **−17.1** | 22% ← ここではもう拮抗しない |
| 28 | −10.1 | 2% |
| 32 | +4.9 | 0% |

**動いた理由**: 1語が短くなるとミス数自体が減り、さらに `orderCount` 増で加点だけが増えるため、
**ミスの罰が相対的に軽くなった**。25 のままだと速さ型に傾き、
「正確に打つ人が早期に落ちる」という**本戦リデザインの動機そのものが再発する**。

> ⚠ 「上位10の速%が50%付近」を基準に採るなら 20〜22 になる。
> **h26 から一貫して「平均順位の拮抗」を採用している**ので 30 とした。

> 🔴 **この数字は sim のダミー実力分布に依存する。** そのダミーは速度とミス率を
> ~~**独立に振っており現実とズレている**（[h33](plan-h33_sim人間モデルの精緻化.md) で是正予定）。~~
> ~~h33 の実装後は**もう一度ここを測り直す**こと。~~
> **是正済み（h33・2026-08-18）。ただし duel は意図的に旧モデルのまま凍結してあるので、
> この表の数字は h33 では動かない。測り直した結果は §2.4 —— 拮抗点は h32 の時点で
> すでに 30 → 22 へ動いており、この表（と `weightMiss = 30`）は現状と一致しない。**

### 2.3 【追記 2026-08-17】h30＋h32 を合成した実測（本番デプロイ後）

h32 単体では分離度が下がり（4380 → 3925）plan-h32 §5 の「現状と同程度以上」を満たさなかったが、
**h30 が逆向きに効くため、両方を入れた合成状態では改善している**。20試合の実測:

| 指標 | h30/h32 前 | h32 単体 | **合成** |
|---|---|---|---|
| 決着時間 | 120.0s | 120.0s | **120.0s（20/20）** |

`orderCount` を上げれば上がり、難度を上げれば下がる。**比（上位/下位）と実力相関の方が安定した指標**。

⚠ **客の提供数が 2025 → 1330（−34%）**。`orderCount` 増と中盤の難度上昇の複合。
本戦では客が逃げないので試合は壊れないが、**行列の見え方は変わる**。実プレイで確認すること。

### 2.4 【追記 2026-08-18】h33 で人間モデルを直したあとの再測定

h30 で「1語が短くなってミスの罰が軽くなった」ぶん 25→30 に上げたが、
**h32 が難度を時間主軸にして序盤から語を伸ばした**結果、ミスの絶対数が増えて罰が再び重くなった、という向き。

> 🔴 **値は変更していない**（設計判断は所有者が決める）。本番は `weightMiss = 30` のまま。
> **推奨は 22〜25 への引き下げ**だが、§2.2 の注記どおり「上位10の速%」を基準に採ると別の値になるので、
> どの基準を採るかを含めて所有者が決めること。判断を保留する場合、
> **「正確に打つ人が有利すぎる」＝本戦リデザインの動機の裏返しが起きうる**ことは認識しておく必要がある。

#### ⑤ 【決定 2026-08-18】`weightMiss` を 30 → **22** にした

所有者の判断で **22 を採用**（基準は h26 から一貫して「平均順位の拮抗」）。
30 のままだと正確型に +25 位傾き、**「ミスを恐れて慎重に打つだけ」のゲームに寄る**。
企画が狙う「速さと正確さの切り替え」が起きないため。

変更後の `make sim`（5 runs / normal）:

> h26(25) → h30(30) → h32(**22**) と3回動いており、**h32 のときは測り直していなかった**。

h33 は plan の指示どおり **duel を相関からも難度追従からも外した**ので、
上表の「現 main」列は h33 の前後で完全一致する（`--sweep-miss` の出力が文字列レベルで同一）。

⚠ したがって **「h33 の後に §5 の weightMiss 再測定をする」という手順は、duel を凍結する限り空振りになる**

## 4. Bot の強さ（P1）

Bot 補完で**常に99人**にするため、**Bot の質が体験を支配する**（人間が少ないほど顕著）。

- Bot が弱すぎる → 人間が上位を独占し、足切りが機能しない
- Bot が強すぎる → 人間が20秒で全滅する

現行 Bot は固定パラメータ（`bot.Config`: `BaseAccuracy` / `BaseElapsedMs` / jitter）で、
**config から調整できる**。当日はこれを手で調整すれば足りる。

> **より本格的な Bot 強化（実データから tier 生成）は h03〜h05（`order_attempt` → プロファイル → tier制）。**
> 本 plan は「当日成立させるための手調整」までを範囲とする。時間が足りなければ h03〜h05 は諦めてよい。
