## 2. A：サーバー側に足すパラメータ

### 2.1 お題レベルのばらつき `odai.levelSpread` ★本命

**現状のコード:**

```go
func (s *Session) wordLevel() int { return s.heatLevel }   // 完全に1対1
```

```go
for i := 0; i < c.orderCount; i++ {
    w := s.words.Next(s.wordLevel(), s.rng)   // 全部同じレベル
}
```

**heat が 13 なら、その瞬間に配られる語は全店・全客・全語が level 13。** ばらつきがゼロ。

これが**単調さの原因のひとつ**。難度が上がる＝全部が一律に難しくなる、という動きしかない。

**提案:**

```go
type OdaiParams struct {
    // LevelSpread は1語ごとの level のばらつき幅（±）。
    // 0 なら現行どおり heatLevel と完全一致。2 なら heatLevel-2 〜 heatLevel+2 から選ぶ。
    LevelSpread int `json:"levelSpread"`
    // LevelOffset は heatLevel に対する下駄。お題だけをやさしく/難しくしたい時に使う。
    // heat をいじると DifficultyUpdate でクライアントの表示も動くので、
    // 「表示は変えずにお題だけ調整したい」という当日の要求に応える。
    LevelOffset int `json:"levelOffset"`
}
```

```go
func (s *Session) wordLevel() int {
    l := s.heatLevel + s.params.Odai.LevelOffset
    if sp := s.params.Odai.LevelSpread; sp > 0 {
        l += s.rng.Intn(2*sp+1) - sp
    }
    if l < 0 { l = 0 }
    return l
}
```

**なぜこれが当日いちばん効くか:**

- 実プレイで「難しすぎる／簡単すぎる」となった時、**`levelOffset` を ±1 するだけで直る**
- `heat.*` を触ると**カーブ全体の形が変わり**、どこがどう動いたか分からなくなる。
  オフセットは**形を保ったまま平行移動**できるので、当日の調整として安全
- `levelSpread` は**同じ heat でも語の長さに幅**が出るので、単調さが減る

> ⚠ `Next()` は**指定レベルに語が無いと下のレベルへ降りる**（`for l := effectiveLevel-1; l >= 0 ...`）。
> 上振れして辞書の上限を超えた場合も、この降下で安全に落ちる。**追加のガードは要らない。**

> ⚠ `wordLevel()` は `s.rng` を消費する。**シード固定の再現性は保たれる**（同じ順序で回るため）が、
> **既存テストの期待値がズレる可能性がある**。`levelSpread` の既定は **0**（現行と完全同一）にして、
> 既存テストを壊さないこと。

### 2.2 足切り予告の件数上限 `cull.warnMaxIds`

**現状:** `internal/game/session.go` に **`const cullWarnMaxIds = 24`** とハードコード。

24 は「初回足切り 99→75 で 24店が切られる」に由来する値で、クライアントにも
「件数上限は24」と回答済み。**根拠のある値なので既定は 24 のまま。**

ただしパラメータにしておく価値がある:

- 当日に**帯域が問題になった場合**、下げるだけで送信量を減らせる（クライアント連携で帯域削減の要望が出ている）
- 逆にデバッグ時に増やして全件見たいこともある

```go
// CullParams に足す
WarnMaxIds int `json:"warnMaxIds"`   // 既定 24
```

> 🔴 **クライアントと合意済みの値なので、当日に勝手に変えない。** 変えるなら必ず共有する。
> 管理画面のヘルプにその旨を書くこと。

### 2.3 足さないもの（意図的に）

| 候補 | 判断 |
|---|---|
| `cutLineRank = 2`（最終ステージの表示） | **足さない**。h22 で決めた3層分離（処理／表示／観測）の**仕様**であって調整値ではない。ツマミにすると当日いじって表示が壊れる |
| `elapsed = 1` / `keys = 1` などの下限ガード | **足さない**。ゼロ除算を防ぐ防御であり、意味のある調整幅が無い |
| `CullStageCount = 6` | **足さない**。固定長配列の長さ。変えるなら型が変わる |
| `bot.*` の拡充 | **h31 の範囲**。本 plan では触らない（§7.1） |

## 3. B：走っている設定を見えるようにする

### 3.1 `configHash` を画面に出す

サーバーは `/api/params` の応答に `configHash`（例 `d0b875b9`）を足して返している
（`internal/configapi/handler.go`）。**しかし管理画面のどこにも表示されていない。**

```
現状: サーバーは出している → 画面が捨てている
```

**管理画面のヘッダに常時表示する。**

- 保存前後でハッシュが変わることで、**保存が本当に届いたか**が分かる
- 別の端末・別の人が触った時に、**同じ設定を見ているか**が照合できる

### 3.2 「未保存の変更がある」ことをもっと強く出す

`dirty` フラグはすでにあるが、**当日は焦って画面を離れる**。

- 未保存の変更があるまま離脱しようとしたら**確認する**（`beforeunload`）
- 変更件数をヘッダに出す（「未保存 3件」）

> これは h24 で「予選で initialLife を DB で変えたのにコードの既定値を見ていた」という
> 混乱があったことへの対策の延長。**設定まわりの事故は毎回「思い込み」から起きている。**

### 3.3 プリセット・履歴が localStorage だけである件

`lib/storage.ts` にコメントがあるとおり、**プリセットも履歴もこの端末の localStorage のみ**。

🔴 **当日、別のPC・別のブラウザから開くと全部消える。**

| 案 | 評価 |
|---|---|
| **① エクスポート/インポート（JSONファイル）** | **推奨**。実装が小さく、Slack等で共有できる。当日の「別の人が引き継ぐ」に耐える |
| ② サーバーに保存する | DBスキーマ追加・API追加が要る。**本戦まで日が無い** |
| ③ 何もしない | 当日に端末が変わると詰む |

**①で進める。** 「現在の設定を JSON で保存」「JSON を読み込む」の2ボタン。

> 生 JSON 表示（`showJson`）はすでにあるので、**コピペで代用もできる**。
> ボタンにするのは、当日に確実に動かすため。

## 4. C：未知のフィールドを自動で出す（★ h30〜h34 の保険）

### 4.1 なぜ要るか

h30〜h34 で **`GameParameters` にフィールドが増える**:

| plan | 増えるもの |
|---|---|
| h30 | `customer.*.orderCount` の値変更（フィールドは既存） |
| h31 | `bot.tiers[3]` ・ `bot.individualSpread` など**大量** |
| h32 | `heat.perElapsedSec` |
| h35（本plan） | `odai.levelSpread` ・ `odai.levelOffset` ・ `cull.warnMaxIds` |

**サーバーだけ先にデプロイすると、管理画面からは新項目が触れない。**
保存では落ちない（`applyEdits` のおかげ）が、**画面に出ないので値を変えられない**。

**本戦が 2026-08-24 で、2リポを常に同時デプロイできる保証は無い。**

### 4.2 どうするか

**受信した JSON とスキーマを突き合わせ、知らないリーフを「その他」セクションに自動描画する。**

```
① 受け取った JSON を再帰的に平坦化してリーフのパス一覧を得る
② スキーマが持つパス（matrix 由来も含む）を引く
③ 残ったパスを「未対応の項目」として、型に応じた素の入力欄で出す
   - number → 数値入力
   - boolean → トグル
   - string → テキスト（読み取り専用でよい）
④ 「⚠ この画面が知らない項目が N 件あります」とバナーを出す
```

**効果:**

- サーバーを先にデプロイしても、**その日のうちに新項目を触れる**
- ラベルもヘルプも無い素の状態だが、**触れないよりはるかにマシ**
- **ミラーのズレが画面上で自動的に可視化される**（ドリフト検出になる）

> ⚠ **これは正式対応の代わりではない。** 落ち着いたら `lib/params.ts` に
> ラベルとヘルプ付きで正式に足す。バナーは「まだ写していない」ことのリマインダーとして機能する。

> ⚠ 逆方向（**スキーマにあるがサーバーが返さない**）も検出して出すこと。
> こちらは「サーバーが消したフィールドを UI が触り続けている」＝**効かないツマミ**で、
> h24 が最も警戒していた事故そのもの。

## 7. 実装上の注意

### 7.1 🔴 h30〜h34 との競合

本 plan と h31・h32 は**同じ `GameParameters` を触る**。

```
h31 → bot.*   に大量追加
h32 → heat.perElapsedSec を追加
h35 → odai.* を新設、cull.warnMaxIds を追加
```

**同時に走らせるとコンフリクトする。** 順序を決めること:

```
推奨: h32 → h35 → h31   （小さい変更から。h31 が最も大きい）
```

どの順でも、**後発は先行がマージされてからブランチを切り直す**。

### 7.2 新グループを足す時の必須手順

`OdaiParams` は**新しいトップレベルグループ**になる。過去に事故があった箇所なので順に確認する:

1. `GameParameters` に追加（**`==` 比較可能を保つ**）
2. `DefaultParameters()` に既定値を入れる
3. **`Validate` に検証を足す**（範囲チェック）
4. **`backfillDefaults` は「新しいグループ」だけ自動で拾う**（#124 で、グループを足すたびに
   列挙を書き足す方式だったのを直した）。**ただし補完はグループ単位**なので、
   🔴 **既存グループに足したフィールドは補完されない**。
   `odai` は新グループなので拾われるが、**`cull.warnMaxIds` は本番で 0 のまま**になる
   （本番DBに `cull` グループが既にあるため）。`warnMaxIds = 0` は「予告を1件も送らない」
   と解釈されうるので、**0 を既定の 24 として扱う補正か、`Validate` での明示的な扱い**を入れること
5. `takoda99-config` の `lib/params.ts` に型・既定値・スキーマを足す
6. `lib/validate.ts` に検証を足す

> 🔴 **4 を疑わないこと。** 本番が既定値で走っていた事故（#124）の原因は
> `backfillDefaults` に `Publish` グループが**列挙され忘れていた**ことだった。
> 現在はリフレクションなので**足し忘れが構造的に起きない**。ここに手を入れる必要は無い。

### 7.3 既定値は「現行と完全に同じ挙動」にする

- `odai.levelSpread = 0` → `wordLevel()` は現行どおり `heatLevel` と一致
- `odai.levelOffset = 0` → 同上
- `cull.warnMaxIds = 24` → 現行のハードコードと同値

**デプロイした瞬間に挙動が変わってはいけない。** 変えるのは運営が意図して値を入れた時だけ。
