## 0. 今やらない理由（実測に基づく）

2026-08-05 の e2-micro 実機計測（`docs/deploy.md`）:

| 項目 | 実測 | 予算に対して |
|---|---|---|
| CPU 合計 | 0.135 vCPU | **54%** |
| メモリ | server 21MB + caddy 49MB | **7%** |
| 接続 | 99/99 成功・エラー0 | — |

**1台で 99人を余裕を持って捌けている**。倍の余裕がある。

さらに設計上:

- ライブ試合状態は **in-memory 単一 goroutine** が最速・最単純。room が直列処理するので session にロックすら要らない
- **tick にネットワークホップ（Redis 往復）を挟むと不利**。150ms tick の中で 99店ぶんの状態を出し入れするのは筋が悪い
- 複数同時試合は**今でも goroutine で並行に動く**（1試合=1goroutine）。インスタンスを増やす必要がない

つまり **Redis を入れると遅く・複雑になるだけ**で、現時点で得るものがない。

## 1. いつやるか（着手の判定条件）

以下のいずれかが**実際に起きてから**着手する。想像で先回りしない。

| 条件 | なぜ Redis が要るか |
|---|---|
| 1台で捌けない負荷が出た | CPU/メモリが実測で予算を超えた |
| 複数インスタンスに分けたい | マッチングプールをインスタンス間で共有する必要がある |
| 再起動で試合が消えるのが許容できない | 状態の snapshot/restore が要る |
| 複数リージョンで運営したい | プール共有 |


`heapMB` が 500 を超える、または CPU が飽和し始めたら検討に入る。

## 2. 今の設計が後付けを許すこと（重要）

**今 in-memory で作っていても後から入れられる**ように、継ぎ目は既に用意されている。

```
room が状態を所有 → StateStore を差して snapshot/restore
```

- `game.Session` は純粋で、`Tick(dt)` と `Results()` で状態を出し入れできる
- `room` が session を所有しており、外から触られない
- `matchmaking` は `Join` / `Leave` のイベント駆動で、プールの実体を差し替えられる

**この構造を壊さない限り、Redis 化は後付けできる。**
逆に言えば、今やるべきことは「Redis を入れる」ことではなく「**この継ぎ目を壊さない**」こと。

やってはいけないこと:

- ❌ `game.Session` の内部状態を room 以外から直接触る
- ❌ matchmaking のプールをグローバル変数にする
- ❌ 試合状態を複数の場所に分散して持つ

## 3. やること（将来・Phase 4）

### 3.1 マッチングプールの Redis 化

複数インスタンスでプールを共有する。

```
Redis:
  takoda99:pool           … 待機中プレイヤーの Set
  takoda99:pool:lock      … 試合編成時の排他
```

**難所**: 「誰がその試合を主催するか」の決定。
複数インスタンスが同時に「99人揃った」と判断すると試合が二重に始まる。
Redis の分散ロック（`SET NX PX`）で1インスタンスだけが編成する。

さらに、待機者の接続は**特定のインスタンスに張られている**ので、
編成したインスタンスと接続先インスタンスが違うと WebSocket を張り替える必要がある。
→ **リダイレクト方式**（「このインスタンスに繋ぎ直して」を返す）が現実的。

### 3.2 試合状態の snapshot/restore

インスタンス障害からの復旧。

```go
type StateStore interface {
	Save(ctx context.Context, matchId string, snapshot []byte) error
	Load(ctx context.Context, matchId string) ([]byte, error)
}
```

`game.Session` に `Snapshot() []byte` / `Restore([]byte)` を足す。

**難所**: 復旧しても**クライアントの WebSocket は切れている**。
再接続してもらい、`MatchStart` 相当の全状態を再送する必要がある。
これは proto の変更（`MatchResume` 的なメッセージ）を伴うので**要承認**。

### 3.3 Redis provider

**Upstash** を想定（`docs/plan/plan-06` の判断を踏襲）。
接続文字列1本で GCP からも Vercel からも繋がる。

> ただし GCP e2-micro（us-west1）から Upstash への往復レイテンシは要実測。
> tick に挟むなら 1ms 未満が必要で、リージョンが離れていると成立しない。
> **その場合は同一VM に Redis を立てる方が速い**（が、それだと冗長化の意味が薄い）。

## 4. 代替案（Redis より先に検討すべきこと）

スケールが要るとしても、Redis が最初の手ではない。

| 課題 | Redis より安い解 |
|---|---|
| 1台で捌けない | **VM を1段階上げる**（e2-small / e2-medium）。$7〜15/月で済む |
| 再起動で試合が消える | **試合の合間にデプロイする運用**（現状の運用ルール）。技術で解く必要がない |
| 複数試合を並行したい | **今でも goroutine で並行に動く**。何もしなくてよい |
| egress が足りない | `StoreListUpdate` の頻度を下げる（Plan-18）。Redis と無関係 |

**「垂直スケール（VMを上げる）で足りるか」を必ず先に検討する。**
99人のイベントで水平スケールが要る状況は考えにくい。
